在高并发、低延迟系统中，SQL 优化很少是“联表查询一定慢”或“必须拆成单表查询”这样简单的判断题。真正需要平衡的是：数据模型、查询形状、索引命中率、网络往返、返回数据量、缓存一致性，以及系统整体的可维护性。

本文给出一套从 SQL 选型到 MyBatis 缓存落地的实践框架，适用于 Java / Spring Boot / MyBatis 与 MySQL、PostgreSQL 等常见关系型数据库组合。

> 核心结论：先把查询写对、索引建对，再根据查询形状决定 JOIN、批量查询或数据冗余；流量真正成为瓶颈时，再用业务缓存承接热点读请求。

## 一、不要用 QPS 单独决定 SQL 形态

“高并发时该一条 SQL 还是多条 SQL”没有固定答案。比并发量更关键的是以下问题：

- 关联是否强且稳定，是否只涉及少量表；
- 返回的是单个对象，还是带有一对多关系的列表；
- 是否需要严格实时的数据；
- 是否存在热点数据、读多写少的特征；
- 索引是否能让过滤、关联和排序高效完成；
- 拆分后增加的网络往返，是否比 JOIN 造成的行膨胀更昂贵。

一个很实用的判断原则是：**数据库擅长集合运算，应用擅长对象组装，缓存擅长承接可容忍短暂过期的热点读。** 不要为“单表”而单表，也不要为“只发一次 SQL”而写出难以优化的大 JOIN。

## 二、四种常见查询方案与选型

### 1. 精简 JOIN：少表、强关联、结果集小

当业务需要在一次请求中得到一个完整的、强关联的小对象时，精简 JOIN 往往是延迟最低、代码最简单的方案。例如会话鉴权、订单归属核验、用户与组织成员关系查询。

```sql
SELECT
    s.user_id,
    s.organization_id,
    u.platform_role,
    m.role
FROM auth_sessions AS s
JOIN users AS u
    ON u.id = s.user_id
LEFT JOIN organization_members AS m
    ON m.user_id = s.user_id
   AND m.organization_id = :organization_id
WHERE s.token_hash = :token_hash
  AND s.expires_at > :now;
```

这类查询的关键不在于“用了 JOIN”，而在于：

- `WHERE` 与 `JOIN ON` 中的关联列必须有合适索引；
- 只返回实际需要的列，避免 `SELECT *`；
- 让驱动表尽可能先通过高选择性条件缩小；
- 通过 `EXPLAIN` / `EXPLAIN ANALYZE` 验证执行计划，而不是凭感觉判断；
- 若查询字段全部在索引中，可减少回表，但不必为了“覆盖索引”盲目堆叠宽索引。

一次 SQL 只有一次应用到数据库的网络往返。对结果集很小的强关联查询，拆成多次查询通常只会增加 RTT、连接池压力与代码复杂度。

### 2. 两阶段批量查询：列表页与一对多关系

列表查询最容易出现性能陷阱。若主表的一行关联多条子表记录，直接 JOIN 会让主表字段在结果中反复复制，造成行数膨胀；分页、排序和总数统计也会变得难以控制。

更稳妥的方式通常是“两阶段批量查询”：先对主表做稳定分页，再批量取关联数据，最后由应用层用 Map 组装。

```sql
-- 第一步：先稳定分页，建议使用游标 / seek 分页替代深 OFFSET
SELECT id, title, author_id
FROM papers
WHERE batch_id = :batch_id
  AND id > :last_id
ORDER BY id
LIMIT :page_size;

-- 第二步：批量获取关联实体；参数由预编译语句绑定
SELECT id, name, department
FROM users
WHERE id IN (:author_ids);
```

应用层可将用户结果转换为 `Map<Long, User>`，再按 `author_id` 填充论文列表。这样数据库只做两次可预测的索引查询，应用负责轻量的内存关联。

实践注意点：

- 不要为每个主表对象单独查询一次关联数据，否则会形成 N+1 查询；
- `IN` 参数数量要有上限，超大集合应分批或改用临时表、数组参数等数据库原生能力；
- 深分页优先考虑 keyset / seek 分页，避免 `OFFSET` 随页码增长而持续扫描和丢弃数据；
- 如果页面确实需要“主对象 + 全部子项”，也可以让数据库返回扁平行，再由应用层去重组装；关键是控制返回行数，而不是机械地禁止 JOIN。

### 3. 反范式与读模型：用写入复杂度交换读取速度

对于读远多于写的详情页、高频展示页，频繁 JOIN 的字段可以冗余到主表或独立读模型中。例如在论文快照中保存作者展示名、学院名称，或者为商品详情维护可直接读取的宽表。

```sql
SELECT id, title, author_name, student_id, department_name
FROM papers
WHERE id = :paper_id;
```

这种设计让热点查询可通过单表主键或唯一索引直接命中，但它不是“免费性能”：

- 更新源数据时要同步更新冗余字段，或通过消息队列异步刷新；
- 必须明确一致性语义：订单、账单等历史记录通常应保留当时快照，而用户资料展示通常应最终一致；
- 需要补偿、重放与监控机制，防止异步更新丢失；
- 数据冗余应聚焦于高频、稳定、展示型字段，避免把整个关联对象无限复制。

本质上，这是 CQRS / 读模型思想的轻量落地：写模型保证数据正确性，读模型为特定读取路径服务。

### 4. 单表查询 + 多级缓存：承接热点读，而非掩盖慢 SQL

当某个接口的读流量极高、数据更新相对少且允许短暂过期时，缓存比继续压榨 SQL 更有效。典型路径如下：

```text
请求
  ├─ L1：进程内缓存（Caffeine 等）
  ├─ L2：分布式缓存（Redis）
  └─ DB：索引良好的单表或小型 JOIN 查询，作为最终数据源
```

缓存命中能显著减少数据库压力，但缓存不是数据库的替代品。至少需要设计：TTL 与随机抖动、缓存穿透防护、热点 key 的击穿保护、更新后的失效或刷新策略，以及缓存不可用时的降级能力。

尤其不要把“`SELECT * FROM table WHERE id = ?`”理解为终极方案。SQL 仍应只取所需字段、使用参数绑定，并建立与查询条件相匹配的索引。

## 三、SQL 设计的通用准则

无论使用哪一种方案，以下原则都比“单表还是 JOIN”更基础：

1. **先测量再优化。** 用慢查询日志、指标和执行计划定位真实瓶颈；关注扫描行数、实际耗时、回表、排序、临时表和锁等待。
2. **索引服务于查询。** 把等值过滤列、连接列、排序列放进索引设计中；联合索引需要遵循最左前缀与选择性，不要只因为某列“经常出现”就建索引。
3. **让结果集保持小而明确。** 不使用 `SELECT *`；限制列表大小；避免在分页查询里不必要地携带大字段。
4. **使用绑定参数。** 防止 SQL 注入，也提高语句复用机会。MyBatis 中优先使用 `#{}`，不要把外部输入直接拼到 `${}`。
5. **控制事务范围。** 事务只包裹必要的读写，不要在事务中进行远程调用、长时间计算或等待用户操作。
6. **连接池和数据库同样重要。** 合理设置连接池上限、超时和排队策略；连接数越大不代表吞吐越高，过量并发可能让数据库在上下文切换与锁竞争中恶化。

## 四、MyBatis 缓存到底缓存了什么

MyBatis 有一级缓存和二级缓存，但它们的适用面远小于“通用业务缓存”。理解边界后，才不会把它们当成 Redis 的替代品。

### 一级缓存：SqlSession 内的本地缓存

一级缓存默认使用 `localCacheScope=SESSION`，作用域是单个 `SqlSession`。相同的查询在同一会话中再次执行时，MyBatis 可以复用结果。缓存键会综合语句 ID、分页参数、最终 SQL、参数值和环境 ID 等信息生成。

它的特点是：

- 缓存只在一个 `SqlSession` 生命周期内有效；
- 执行更新语句，或调用 `commit`、`rollback`、`close`、`clearCache` 等操作时，会导致相关本地缓存失效或清空；
- 在 Spring 的事务管理下，带有 `@Transactional` 的同一事务通常复用同一个 `SqlSession`，重复执行完全相同的查询才可能命中；
- 没有事务边界时，常见的 Spring 集成会在一次 Mapper 调用后归还会话，因此跨 Mapper 调用通常不要期待一级缓存命中；
- 如需降低本地缓存作用范围，可设置 `localCacheScope=STATEMENT`。因此“一级缓存无法关闭”的说法并不准确。

一级缓存适合被动地消除事务内重复查询。它不适合被当作跨请求性能方案，也不应该依赖它保存可变对象状态。

### 二级缓存：Mapper Namespace 级缓存

二级缓存按 Mapper namespace 隔离，可跨 `SqlSession` 复用。它需要全局开启缓存配置，并在对应 Mapper 中显式声明 `<cache/>`（注解方式也可配置）。同一 namespace 内的增删改在提交时，通常会清空该 namespace 的二级缓存。

二级缓存并不总是“序列化后的字节数据”。其行为取决于缓存实现和 `readOnly` / `readWrite` 设置：

- 默认的读写缓存倾向于通过序列化获得对象副本，此时缓存对象需要可序列化；
- `readOnly=true` 可直接返回对象引用，开销更小，但调用方不得修改对象；
- 不同缓存实现（例如第三方缓存适配器）也可能有不同的存储与复制策略。

### 为什么生产系统通常慎用二级缓存

二级缓存最大的风险来自失效边界，而不是命中率。

假设 `UserMapper` 缓存了一条用户与部门的 JOIN 查询结果；随后 `DepartmentMapper` 更新部门名称。后者只会清理自己的 namespace 缓存，`UserMapper` 中的联表结果不一定会同步失效，因而可能返回旧部门名称。

此外，默认二级缓存是单个应用进程内的缓存。多实例部署时，各实例的缓存彼此独立，数据更新后容易出现节点间短暂甚至持续不一致。基于这些原因，中大型分布式系统通常采用：

- 保留并自然利用一级缓存；
- 对 MyBatis 二级缓存默认保持谨慎，尤其避免缓存跨表、频繁更新或一致性敏感的数据；
- 在 Service 层使用 Spring Cache + Redis 等共享缓存，将 key、TTL、失效与刷新策略作为明确的业务设计。

## 五、推荐的落地路径

可以按以下顺序推进，而不是一开始就重构为缓存架构：

1. 为核心接口建立基线：QPS、P95/P99 延迟、慢 SQL、扫描行数、缓存命中率。
2. 审查 SQL：删除无用字段和 N+1 查询，为过滤、关联和排序建立正确索引。
3. 小结果集的固定关系使用精简 JOIN；列表及一对多关系采用分页主查询 + 批量关联查询。
4. 对稳定、高频、读多写少的数据建立冗余读模型，并明确最终一致性与补偿方案。
5. 对确认存在热点的读接口引入 L1/L2 缓存，先定义失效语义，再实现缓存逻辑。
6. 保持 MyBatis 一级缓存默认行为；启用二级缓存前，逐项评估跨 Mapper 更新、集群一致性、对象可变性与失效成本。

## 六、结语

高并发、低延迟并不要求所有查询都拆成单表，也不要求所有数据都塞进缓存。少表且强关联的小查询，精简 JOIN 通常最优；列表的一对多数据，更适合分两阶段批量查询；热点详情读则可用冗余读模型和多级缓存承接流量。

把优化重点放在查询形状、索引、结果集大小与一致性边界上，才能既快，又能长期稳定地演进。
